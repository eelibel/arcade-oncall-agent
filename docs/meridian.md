# Meridian Mutual Insurance — the customer this build serves

Meridian Mutual is a fictional Fortune-2000 P&C and group-benefits insurer: ~$14B revenue, ~24,000 employees. Okta is the identity provider; security posture is customer-VPC / self-hosted for anything near claims or member data. An AI governance board and the CISO can each veto new systems.

After a CEO-level "AI-first operations" push, every business unit wants agents. The AI Platform Team — six people — runs the internal machinery (CI/CD, deployment platform, shared services) and fields those requests. Their twin fears: becoming the bottleneck, or becoming the headline. A platform engineer on this team leads technical validation of Arcade; the budget belongs to the CTO.

The validation strategy: dogfood on the platform team's own stack first, prove the control pattern, then extend the same governed path to business units. The control pattern — agent proposes, human approves, action executes — is the thing being validated; every future Meridian agent inherits it.

## ClaimsCore — the shared capability

Meridian's internal claims system, faked here as a small API (claim status by ID, coverage by policy number) and wired into Arcade once as a custom toolkit. Both use cases call it, and every call runs with the permissions of the person asking — the on-call engineer's impact check runs as her, Amara's client answer runs as Amara. No shared service account: so the platform can answer "who touched claims data, and when." For an insurer with a governance board, that per-person attribution is the point.

This demo runs on Arcade's hosted tier with fictional data; Meridian's production posture would place the same engine and toolkit inside their VPC — identical architecture, different placement.

One limit the team records honestly: grants are per-tool, not per-record. Amara can be allowed or denied the claim-status tool, but "only her own clients' claims" cannot be expressed at the platform layer today — that scoping lives inside ClaimsCore itself.

## Use case 1 — Incident triage (platform team, dogfood)

An engineer files a GitHub issue: CI runners are timing out and blocking the claims-service deploy — and that deploy carries the hotfix for a claims-intake bug already delaying a customer claim in production.

The triage agent is not a chatbot and does not run continuously. In production, the filing of the issue fires it via webhook; in this demo it is started manually (one command, same code). It runs unattended but on a human's authority: PagerDuty says who is on call, and the agent operates under that engineer's standing delegation — it can be triggered at 3am while she sleeps, but its permissions are hers, its actions are attributed to her, and its writes wait for her.

The run: read the issue, search past issues for duplicates (closed ones included — that's where resolved history lives), pull recent commits for suspects, ask PagerDuty who is on call, check claim impact via ClaimsCore, and draft a Slack message for #incidents: summary, probable cause, prior occurrence and how it was fixed, business impact, suggested page. Hard stop — the on-call engineer approves before anything posts. Automation solved notification years ago; the agent compresses interpretation (the 15–25 minutes of context assembly per incident).

The same governed path has a second front door: the on-call engineer's own AI assistant. Mid-incident, Priya asks ad-hoc questions from her desktop — what's the latest on the issue, did anyone touch the runner config, are claims backing up, who takes over tonight — through the same tools, under the same permissions, leaving the same audit trail. Pipeline and conversation are two consumers of one governed capability, not two systems.

### How the platform team stress-tests it

The happy path shows the agent working; validation is the team deliberately poking at it. Each probe records what happened — confirmed, absent, or blocked — with the screenshot or log line that shows it. A problem that *doesn't* appear gets written down too.

- **Attribution.** After Priya's run, she opens GitHub, Slack, and PagerDuty and checks what each displays as the actor on the agent's actions. If the governance board asks "who touched claims data, and when," the answer has to come from those systems' own records, not from our notes. Three screenshots.
- **Jordan's run.** Jordan, two months in and holding read-only access, starts the identical triage — the preview of every less-privileged user who will ever inherit this pattern. It should sail through the reading steps and stop cold at the Slack post. What does the stop look like on his screen — a clear "you don't have this," or a cryptic error? Capture the moment, including any runtime authorization prompt.
- **Two fences.** Same blocked action, two different causes — the test is whether the platform tells you which. Setup: the team's admin opens the agent's project configuration in the Arcade dashboard and removes the Slack toolkit from the tools this agent may use. Priya's own grants are not touched — she authorized Slack posting in the happy path and that grant still stands. The run: Priya re-runs the exact same triage command. Expected: GitHub, PagerDuty, and ClaimsCore steps succeed; at the Slack step the agent fails — not because Priya lacks permission, but because the tool is no longer available to this agent. What to look at: the error. Put it next to Jordan's error from his run. Jordan's stop should ask *him* for authorization (his grant is what's missing); Priya's stop should say the tool is unavailable to this agent — asking her would be pointless, since her grant was never the problem. Capture: both error messages side by side, and one written sentence: could an engineer debugging at 2am tell these two failures apart in under a minute? If the dashboard has no per-agent tool configuration at all, that absence is the recorded result. Restore the toolkit afterward.
- **One action, two approval mechanisms.** The same act — posting the incident update to #incidents as Priya — happens twice, and we compare what "approved" meant each time. Run 1, the pipeline: the script prints the complete draft in the terminal, waits for Priya to type y, appends a line to `approvals.log` (timestamp, approver, draft hash), then posts. Run 2, the desktop assistant: Priya asks for the same update to be posted; the only checkpoint before the post is the chat app's built-in tool-permission popup — a generic "Allow Slack_SendMessage?" that shows a tool name, not the draft. Capture: terminal screenshot plus the `approvals.log` line; desktop screenshot of the popup. Then fill a four-row comparison in [decisions.md](http://decisions.md): Did the approver see the exact content before approving? Is the approval recorded anywhere queryable afterward? Who decided a checkpoint existed at all — us, or the chat app's vendor? Would the same checkpoint exist on a different chat product? Run 1 answers yes / yes / us / yes-it's-our-code; Run 2's answers are the finding.
- **One Meridian rule.** Katherine's requirement, verbatim: "engineers on the incident-response rotation may post to Slack through agents; read-only engineers may not." The team's admin tries to make the dashboard say that sentence. Steps, in order: (1) find the Users / Teams / Roles area; (2) create two roles — `incident-responders` containing Priya, `engineers-readonly` containing Jordan; (3) look for any way to attach *tool access* to a role — specifically, allow `Slack_SendMessage` for the first role and deny it for the second; (4) whatever was configurable, verify it empirically: Jordan attempts the Slack post again — did anything behave differently than before the roles existed? Capture: a screenshot at each step, and the closing sentence in this form: "The rule as stated can / cannot be expressed. The model stops at: ___" — for example, "roles exist but govern dashboard administration, not tool access." If step 1 finds no roles area at all, that is the stopping point.
- **A hook.** A hook is a small piece of our code that Arcade runs before each tool call — the docs claim pre- and post-call hooks exist. Sixty minutes total, then stop regardless. Minutes 0–30: search the docs for how to register one on our plan (config file, dashboard, SDK). If it's gated to a higher tier, screenshot the gate — that's the result, done. If available: write ~15 lines that do two things on every call: append a line to `events.log` (timestamp, user, tool, argument summary), and reject any `Slack_SendMessage` whose text contains `@channel` — Meridian's plausible house rule that agents never mass-ping. Then two runs: triage with a draft deliberately containing `@channel` (expect: blocked, with our rejection message), and a clean run (expect: passes). Capture: the hook code, both outcomes, and `events.log` showing every call from both runs.

## Use case 2 — Client servicing / meeting prep (business unit)

Amara, a group-benefits account manager, preps for a client renewal from her own AI assistant on the desktop — the interactive surface, no pipeline involved. It reads her Calendar, Gmail, and Docs, drafts the prep brief, sends the follow-up summary to the client, and when the client calls about a claim, answers live via ClaimsCore. Same governed path as use case 1, different buyer mode: productivity agents for business users, reaching internal systems safely, every access attributed to Amara personally.

### Two probes on Amara's path

- **The rules surface.** Same goal as the hook — stop a bad call before it executes — but through the product's own no-code policy feature (Contextual Access) instead of our code. This runs *before* the deliberate failure, because the failure is read against it. Katherine's rule for business users: "agent-drafted outbound email must not contain CONFIDENTIAL." The admin's steps: (1) find the Contextual Access / policies area in the dashboard; (2) attempt to create a rule targeting the Gmail send tool that inspects the call's *content* — body text or attachment name — for the word CONFIDENTIAL; (3) record two facts separately: does the rule-building UI exist on our tier at all, and can a rule reference call content, or only allow/deny a tool wholesale; (4) if a rule saved: Amara sends her follow-up with "CONFIDENTIAL" in the attachment name — does it block? Capture: screenshots of the policy UI (or its absence), the rule as saved, the send outcome.
- **The deliberate failure.** Amara's assistant drafts the client follow-up with a file attached — every grant legitimate — and sends it. Which file depends on the previous probe: if no rule could be created, the file is plainly marked CONFIDENTIAL in its name; if a rule caught the literal word, the file's name is innocent and only its contents are sensitive — demonstrating that rules catch what can be named, not what things mean. Either way the send completes and nothing intervenes. One screenshot, one paragraph. This is the line between what today's controls catch and what they don't, shown rather than claimed.

## One check across everything

Last, the team exports whatever the platform's dashboard offers about all of these runs — Priya's, Jordan's, Amara's — and lays it next to the questions a security reviewer would actually ask. The gap list is the result.
